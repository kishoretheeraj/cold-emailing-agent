# Phase 2.5 — Auto-Apply Agent Design

**Status:** design complete, pending user review before `writing-plans`.

**Supersedes:** the Phase 2.5 stub in
`docs/superpowers/specs/2026-08-26-full-fledged-job-platform-buildout.md` (lines ~150-169). That
stub's "review queue + auto-apply toggle" framing and its CI-safety note (submit gated behind a
local-only env var, never a GitHub Actions secret) both carry forward into this design, made
concrete. Phase 3 (resume intelligence) already absorbed the stub's "resume generation" bullet;
this spec adds the actual submission action on top of Phase 3's output, plus a job-selection layer
Phase 2 never had.

**Spec:** none upstream beyond the buildout stub above — this document is the spec for this phase.

---

## Global Constraints

These are non-negotiable and apply to every component below, not just the ones where they're
called out:

- **Never bypass CAPTCHA or bot-detection**, in any form, including "stealth" browser patching.
  If a page presents one, that row is flagged and skipped, permanently.
- **Never create an account on the user's behalf**, on any platform.
- **Never submit a real application without a human's explicit, per-instance approval** — a
  standing "yes, always submit" setting does not satisfy this. The approval tap is the one
  required human action anywhere in this pipeline.
- **Never fabricate content.** Every generated field — screening-question answers, cover-letter
  text — must be grounded in the user's real profile data (the same `master.json`/`metrics.json`
  corpus Phase 3 already uses), never invented.
- **A missing/unclear signal always degrades to "skip and flag," never to a guess.** Same posture
  as the H-1B visa gate and Form D funding signal elsewhere in this codebase: absence is
  "unhandled," not a negative or a best-effort fabrication.
- **`build-continue.yml` (the hourly unattended implementation workflow) must never be able to
  trigger a real submission**, even while building and testing this phase's own code. The actual
  submit path is gated behind an explicit "armed" signal that only the real approval-triggered
  GitHub Actions run ever sets — see "Submit-safety gating" below. This carries forward the
  buildout stub's own CI-safety note.

## Architecture overview

```
┌─────────────────────────────────────────────────────────────────────────┐
│  DISCOVERY (existing, unchanged code — job_discovery.py, jobright.py)   │
│  writes job_applications rows at stage='saved'                          │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │
┌───────────────────────────────▼───────────────────────────────────────┐
│  JOB-PICK ENGINE (new — job_pick.py)                                    │
│  Stage 1: structured filters  →  Stage 2: embedding similarity          │
│  →  Stage 3: LLM-judge (coarse strong/maybe/no)                         │
│  "strong" only → auto-triggers Phase 3's resume_agent propose+build     │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │  (rows with resume_file_ref + cover_letter_file_ref set)
┌───────────────────────────────▼───────────────────────────────────────┐
│  PLATFORM CLASSIFIER (new, inside apply_agent.py)                       │
│  Greenhouse / Ashby / Lever → hand-mapped filler                        │
│  Any other real application page → browser-use (generic LLM filler)     │
│  Workday, aggregator/listing links → excluded, flagged, never attempted │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │
┌───────────────────────────────▼───────────────────────────────────────┐
│  PREVIEW PASS (unattended, scheduled — apply_agent.py --preview)        │
│  fills every field, attaches resume/cover letter, answers screening     │
│  questions, stops before Submit, stage → 'ready_to_submit'              │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │  (contact-manager review UI, any device)
┌───────────────────────────────▼───────────────────────────────────────┐
│  APPROVAL TAP (human, the one required action)                          │
│  fires a workflow_dispatch with the job_applications id                 │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │
┌───────────────────────────────▼───────────────────────────────────────┐
│  SUBMIT PASS (apply_agent.py --submit <id>, armed-only)                 │
│  fills fresh + submits in one pass, stage → 'applied'                   │
└──────────────────────────────────────────────────────────────────────┘
```

Nothing in this pipeline requires the user's laptop to be open except the approval tap itself,
which can happen from any device.

## Component 1 — Job-pick engine (`job_pick.py`, new)

Replaces the crude `target_roles` word-overlap check currently in `job_discovery.py` with a
three-stage funnel, run as a step appended to `jobright_pull.yml` (and manually after
`job_discovery.py` runs) against every `job_applications` row at `stage='saved'` with no
`pick_verdict` yet.

**Stage 1 — structured filters.** Deterministic, free: location, employment type, seniority,
explicit title overlap. This is today's filter, kept as the cheap first gate, not the whole
system.

**Stage 2 — embedding similarity.** Rows surviving Stage 1 get their job description embedded and
compared (cosine similarity) against the user's real structured profile — the same
`master.json` bullet-point achievements and skills Phase 3 already uses, not a vague summary. This
is the technique behind Resume-Matcher (github.com/srbhr/Resume-Matcher), replicated directly in
our own small function rather than importing their harness. No LLM call, no per-job API cost.
Produces a numeric `pick_score`.

**Stage 3 — LLM-as-judge, only on what survives Stage 1 and 2.** The smallest, most expensive
gate, deliberately last. Uses a **coarse three-band rubric** — `strong` / `maybe` / `no` — not a
continuous score. Research surfaced during this phase's design showed LLM-judge alignment with
human judgment tops out around 85% even on strong models and gets measurably worse with
fine-grained scoring; since nothing catches a wrong "yes" downstream (see Global Constraints),
only `strong` verdicts proceed. `maybe` and `no` both just sit at `stage='saved'`, visible in
`/applications` for the user to act on manually if they want — never silently discarded.

**Zero-tap resume trigger.** A `strong` verdict immediately calls `resume_agent.py`'s existing
`propose()` then `build()` back to back, with no pause between them. This is a deliberate
loosening of Phase 3's original human-strategy-review gate, but **only for this auto-pick path** —
a human running `resume_agent.py --propose`/`--build` manually from the CLI still gets whatever
gap they naturally leave between the two commands. Flagging this explicitly since it's the one
place this phase changes an existing, deliberately-designed gate rather than adding a new one.

**New `job_applications` columns:** `pick_verdict` (`strong`/`maybe`/`no`), `pick_score` (numeric,
Stage 2's cosine similarity), `pick_reasoning` (text, Stage 3's brief rationale — for debugging why
a call went the way it did, same spirit as `resume_strategy` being inspectable).

**New `usage_tracking` wiring:** Stage 2's embedding call and Stage 3's judge call both log through
the existing `usage_tracking.log_usage` (`module="job_pick"`, `action="embedding"` /
`"judge"`), same as every other Claude call in this codebase.

## Component 2 — Platform classifier

Pure function, no I/O: given a `job_url`, classify it as `greenhouse` / `ashby` / `lever` /
`workday` / `aggregator` / `generic`. Pattern-matches the URL (same style as the platform-bucketing
query used during this phase's own research — `ashbyhq.com`, `greenhouse.io`, `lever.co`,
`myworkdayjobs.com`/`wd\d+\.myworkdayjobs.com`, and a fixed list of known aggregator/listing
domains — `indeed.com`, `ziprecruiter.com`, `ycombinator.com/companies` — that are never real
application pages). Anything not matching a known pattern falls to `generic`, not `workday` or
`aggregator` — the exclusion list is a specific, named set, not "anything unfamiliar."

`workday` and `aggregator` rows are never attempted. This isn't a "not built yet" gap — see
"Rejected, not deferred" below for why.

## Component 3 — Preview pass (`apply_agent.py --preview`)

Runs unattended (new GitHub Actions workflow, `apply_agent_preview.yml`, scheduled — mirrors
`jobright_pull.yml`'s shape). Queries `job_applications` for rows at `stage='saved'` (or
whatever stage Component 1 leaves `strong` rows at) with both `resume_file_ref` and
`cover_letter_file_ref` set, and a platform of `greenhouse`/`ashby`/`lever`/`generic`.

For each eligible row, one at a time (never parallel — same reasoning as this codebase's existing
"never run two email drafts at once" rule):

- **Greenhouse / Ashby / Lever** → hand-mapped filler. Each platform gets its own small module
  under a new `ats_fillers/` package (mirrors this codebase's existing per-concern module
  convention). Deterministic field-to-selector mapping, built once per platform, not re-derived
  per job.
- **Generic** → `browser-use` (github.com/browser-use/browser-use, MIT license). No CAPTCHA-solving
  built in — this is exactly why it was chosen over Skyvern during this phase's research, which
  ships CAPTCHA-solving as a core feature and was rejected on that basis alone. Driven by our own
  Claude API key, same governance as everywhere else in this codebase.

Both paths share the same field-value sources:

- **Standard fields** (name, email, phone, location, LinkedIn) — deterministic, from the user's
  profile data.
- **Resume / cover letter** — attached via headless file input (`setInputFiles`-equivalent; both
  Playwright and `browser-use` support this natively, confirmed during this phase's research —
  no OS dialog, no third-party dependency, no JobRight involvement).
- **Free-text screening questions** — read off the page, answered by Claude, grounded only in the
  user's real profile facts. Same non-fabrication governance as Phase 3's cover-letter generator.
- **Sensitive fixed-answer questions** (work authorization, visa sponsorship, EEO — race, gender,
  disability, veteran status, LGBTQ+) — **never LLM-generated per application.** Pulled from one
  new canonical profile block, stored as a new `prompts` table row (`applicant_eligibility`,
  JSON-encoded text) — reusing the existing `db.load_prompts()`/`db.upsert_prompt` infrastructure
  rather than a new table, editable live via the contact-manager's existing Prompts page. Mirrors
  the exact shape of JobRight's own "Equal Employment" profile tab, observed live during this
  phase's research.
- **Anything unrecognized** — stop, log it, move to the next job. Never guess.

On success, the row's `stage` moves to a new value, `ready_to_submit`, and a new
`apply_preview` JSONB column stores every filled value plus the generated screening-question
answers — enough for the review UI to show exactly what would be submitted without needing a live
browser session. No browser tab or automation session stays open between the preview pass and the
eventual submit pass.

**Per-row failure isolation**: one company's page failing (layout change, unexpected field,
timeout, a CAPTCHA wall) never blocks the rest of the run — same posture as `job_discovery.py` and
`visa_match_new.py`. A blocked row gets a `apply_blocked_reason` (new text column) and stays at
`stage='saved'`, visible in `/applications` for the user to handle by hand.

## Component 4 — Review UI (contact-manager)

Extends the existing `/applications` page (not a new page) with a filtered view for
`stage='ready_to_submit'` rows, showing each `apply_preview`'s filled values and the generated
screening-question answers in plain, readable form. One "Approve & Submit" action per row.

Approving calls a new API route, `POST /api/applications/[id]/submit`, which fires a
`workflow_dispatch` on a new `apply_agent_submit.yml` workflow with the row's id as input — the
exact same trigger pattern the existing "Run Agent" button already uses for `daily_agent.yml`
(`GITHUB_DISPATCH_TOKEN`, `actions: write`). No new trigger mechanism to design; this one is
already proven in this codebase.

## Component 5 — Submit pass (`apply_agent.py --submit <id>`) and submit-safety gating

Runs inside `apply_agent_submit.yml`, triggered only by the approval tap's `workflow_dispatch`.
Re-fills the form fresh (does not reuse the preview pass's browser state — no idle session to keep
alive) using the same field-value sources as Component 3, then submits.

**Submit-safety gating**, carrying forward the buildout stub's CI-safety note: the actual submit
call inside `apply_agent.py` is gated behind an explicit `APPLY_AGENT_ARMED` environment variable.
This variable is set **only** inside `apply_agent_submit.yml`'s own job definition — it is never a
repo-level GitHub Actions secret, never present in `build-continue.yml`'s environment, and never
set by any test or local dry-run invocation. This makes it structurally impossible for
`build-continue.yml` (which pushes straight to `main`, unattended, hourly, with no PR review) to
ever cause a real submission while it builds or tests this phase's own code — its test runs simply
never have `APPLY_AGENT_ARMED` set, so the submit call is a guaranteed no-op path in that
environment regardless of what the test exercises.

On success: `stage` → `applied`, `source_channel` set to the platform, `applied_date` set to today.

## Rejected, not deferred

- **Workday.** Two independent, structural blockers surfaced during this phase's research: Workday
  runs a separate tenant per employer, generally requiring a new candidate account per company
  (account creation is a hard constraint above), and Workday-class sites are exactly what modern
  anti-bot systems target — the standard industry workaround is stealth-patching the browser,
  which is bypass territory (also a hard constraint above). This isn't "not built yet" — it's a
  permanent exclusion. Workday rows stay at `stage='saved'` forever unless the user applies by
  hand.
- **JobRight as the filling mechanism.** Explored at length during this phase's brainstorm — their
  extension can attach a library resume via a real "Original Version" mechanism, and their
  Chrome autofill itself is well-regarded externally. But it only runs inside a live, open
  browser session with their extension installed, which cannot satisfy the "runs with the laptop
  closed" requirement no matter how it's driven. The user has since cancelled the JobRight
  subscription; `jobright.py`'s discovery puller (a separate, already-shipped feature, confirmed
  still working on the free tier during this phase's investigation) is unaffected and stays.
- **Skyvern** as the generic-filler library — technically capable, but ships CAPTCHA-solving as a
  core built-in feature, a direct conflict with the CAPTCHA constraint above even if that specific
  function is never called. `browser-use` (MIT, no CAPTCHA-solving) was chosen instead.
- **AI-content-detection evasion** — not part of this phase, consistent with the same rejection
  already recorded in Phase 3's design.
- **Resume-attach-on-reply** (generating and attaching a tailored resume to a cold-email reply
  when a contact asks for one) — a real, separate, smaller feature raised during this phase's
  brainstorm. Deliberately out of scope here; it touches `reply_drafter.py` and `gmail.py`'s
  `create_draft`, not the job-application pipeline, and gets its own future spec.

## Testing approach

Follows this codebase's established patterns throughout — every new function ships with tests,
all outbound calls (Anthropic, Supabase, the ATS pages themselves) mocked, never touching real
network in tests:

- `job_pick.py`: parametrized tests per stage (structured-filter pass/fail cases, embedding
  similarity with fixture vectors, judge-verdict mapping), plus a never-raises sweep matching
  `visa_match_new.py`'s pattern for per-row failure isolation.
- Platform classifier: pure function, exhaustive URL-pattern test table (one row per platform,
  including the aggregator-domain exclusions).
- `apply_agent.py`: mocked browser-automation layer (both the hand-mapped fillers and the
  `browser-use` call site), asserting the right field-value sources are used for each field
  category, that unrecognized fields short-circuit to "flag and skip," and that
  `APPLY_AGENT_ARMED` being unset makes the submit call a guaranteed no-op — this last test is the
  one enforcing the CI-safety constraint above and should be treated as load-bearing.
- Contact-manager: new Vitest cases for the `/applications` review-queue filter and the new
  `/api/applications/[id]/submit` route (mocking the `workflow_dispatch` fetch call, same pattern
  as the existing "Run Agent" button's test), plus a Playwright e2e case for the approve action.
